# Plan 030: rebuild vit-store

Status: research done, end state agreed, foundation next. Revised 11-18: Solid 2.0 went stable, Effect runs the server, browsers reach it through server functions over Effect RPC, and the backend and admin come before the storefront. Items marked (open) wait on my answer.

Every agent working on the rebuild reads this whole file first. If you hit something this file doesn't answer, ask me. Don't guess my intent from old docs, because most of them predate this plan.

## Why

This codebase is an artifact. It's been built by every model since Sonnet 3.5, and you can tell. Workarounds on workarounds, two UI kits, raw SQL casts everywhere, analytics that swallow errors, stock math that's wrong on cancel and refund. Fixing vit-store feels better than starting over somewhere else, so vit-store stays the repo. But almost everything inside it gets rebuilt.

The goal: mom packs boxes and decides what to buy. Software does everything else. Buyers find the right product fast, pay in a few taps, and come back.

## Who uses it

- Mom runs the admin on her phone 90% of the time and on an iPad the other 10%. Phone first, always.
- I use the admin on a laptop and ask agents questions about sales.
- Buyers are mostly on phones, a lot of them cheap old Androids on mobile data. The storefront has to be fast there, not just on my laptop.
- Agents. They call the API, answer my sales questions and build features. They're users too.

## What I want

### Stack, decided

- All UI is Solid 2: storefront and admin. Solid 2.0.0, `@solidjs/router` 2.0.0 and `@solidjs/vite-plugin` 3.0.1 went stable on 11-18. Betas and RCs of other libraries are fine, this is my project. Use server frames and server components where they actually help.
- Effect on the server, never in the browser. The API's domain is Effect, copied from amerik-vitamin: orders, payments, stock moves, the outbox, QPay reconcile, unpaid expiry, SMS, purchases, Firecrawl lookups and bot tools. Its typed errors and `Schedule` cover the money paths and crons, which is where vit-store's costly bugs were. No browser bundle imports `effect`, because its RPC client alone is 56 KB gzipped against the storefront's 45 KB budget. Effect is pinned exactly and bumped in its own PR, because amerik went from 4.0.1 to 4.1.4 in a month and its import paths moved. This reverses the 11-14 "no Effect in the backend". The comparison is `~/dev/scratchpad/vit-store/shots/page/effect-or-not.html`. App code never imports from `infra/`.
- Effect RPC is the API, and the API is an SDK. One `RpcGroup` in `packages/contract`, served by `RpcServer` on the API Worker. Every caller goes through it: the storefront and admin from server functions, the bot Worker over its service binding, agents and scripts over HTTPS with an API key. Auth, rate limits and the error log live in that one place, and the SDK can do everything the apps can. No oRPC. No MCP for now. `effect/ai/McpServer` can expose the group later.
- Browsers reach the API through Solid server functions. Pages read with the router's `query` and `liveQuery`, and write with `formAction` and Solid's `action`. Those call file-level `"use server"` modules under `src/server/`, which run `ApiClient` over the API service binding, the way amerik's `apps/web/src/api/binding.ts` does during SSR. The browser carries no RPC client and no schema library.
- Effect Schema is the one schema library. Schemas live in `packages/contract` next to each Rpc, as amerik's `@amerik/contracts` does. No valibot, no zod. Outputs are `Schema.Struct`, not `Schema.Class`, so a value that crosses a server function as plain data still matches its type.
- Types flow db to contract to UI. No OpenAPI codegen step.
- Drizzle RC with a new db schema. The rebuild owns the `shop` migrations after the fork, and the new schema is amerik-vitamin's `shop` schema (`~/dev/amerik-vitamin/packages/db/src/schema.ts`). It was designed from vit-store's mistakes: uuid ids, a stock move log, order events, payments as a ledger, slug history, Better Auth tables, supplier orders, an outbox. amerik-vitamin's migrations are frozen, so only this repo migrates `shop`. Copy it with its Effect `Database` service (`drizzle-orm/effect-postgres` over `@effect/sql-pg`), fill the gaps vit-store needs, and migrate the data with its legacy import as the starting point. Its rules come along too: `docs/COMMERCE-RULES.md` and the "bugs to never repeat" list in `docs/LEGACY.md` over there. Don't carry old mistakes forward to stay compatible.
- Better Auth. Admins sign in with Google. No passkeys, no shared bot token, no KV sessions nobody can revoke. Agents get scoped API keys.
- The `shop` schema gains three tables: restock requests, deliveries and product images.
- Alchemy 2 beta. CI is the only thing that deploys. Every PR gets its own preview stage.
- No second infra provider and no Neon. Dev, previews and staging use one Postgres on my dev box, reached through its `dev-box` Cloudflare Tunnel and Hyperdrive with an Access service token. Each PR gets its own database there. Previews being down while the box is off is fine. Prod stays on the existing Postgres.
- The new stack runs on staging for a while before it touches prod. Staging lives on the dev box, so the soak is mom and me placing real orders, not customers.
- Axiom keeps logs and traces and sends alerts. Monitors and a Telegram notifier are Alchemy resources in `infra/` through `@alchemy.run/axiom`, so an alert is reviewed like code. Errors are typed.
- `vp` for everything. Bun goes. `vp dev` is the one local command: it starts Postgres, migrates, seeds synthetic fixtures and runs every Worker.
- Tailwind v4, with `@shadcn/lint` enforcing the design system. Rules agents can verify beat rules in a doc.
- CI gates. Type checks run on tsrs, not tsgo.
- Delivery fee is 6,000.
- Purchases get the new flow amerik-vitamin built: supplier orders imported from Amazon order history, grouped into batches by delivery burst, counted on arrival, the rest closed as not coming, and a suggested price in 5,000 steps that mom can edit. The rules are in amerik's `docs/COMMERCE-RULES.md`, the backend in its PR #27, which comes over as Effect code, and the screens' flows in its PR #30. amerik's `closeBatch` works around the Effect drizzle builder rendering a subquery as an empty `in ()`. The workaround comes along with its comment.
- The customer Messenger bot gets rebuilt on Pi Durable (`@earendil-works/pi-durable`, pinned exactly) with one Durable Object per Messenger thread, deployed by Alchemy. It sells full time and hands off to mom or me when it should, like erxes frontline's bots. Its tools call the Effect RPC SDK, every message is mirrored to Postgres, and mom reads and takes over chats in the admin. Pi is experimental and its storage only rolls forward, so upgrades are deliberate PRs. The Telegram admin assistant stays on the old Worker until A6 and P4 land.

### Rules from the audit

Each of these becomes a lint rule or a CI gate, and each rule's message names the correct fix.

- No `.catch(() => 0)` or any catch that turns an error into a default value. Errors stay errors all the way to the UI.
- One cache layer, purged by the code that writes. Stock is always read live.
- Typed errors: every Rpc declares its error schema. One `onError` that logs once, one db client per request.
- No `effect` in a browser bundle. size-limit and `vit/effect-server-only` both fail it.
- Package exports are explicit. No `"./*"`.
- No complexity disables, no lint-disable comments.

### How it looks and feels

- Seamless, playful, fun animations. Tasteful background hues. Never distracting, never in the way of buying.
- The admin keeps today's functionality, route by route in "Admin parity" below, and gets bold UI and UX improvements. It's rebuilt before the storefront. PR #373's cream look, which I like much better than the old UI, is the starting point, not the limit. D0b prototypes the new look on a 390 px phone and I pick before D1 builds it. amerik's screens bring their flows, not their look.
- Fast on cheap phones beats every animation. If an effect costs frames on a slow Android, it goes.

### Storefront

- Order flow is the most important thing in this repo. Browse, product, cart, checkout and payment. Checkout becomes one page: cart, phone, address, payment method and one pay button.
- Unpaid orders are the biggest leak. Lifetime, ₮51.3M got paid and ₮38.2M was ordered and never paid. Since September, first-time buyers paid 82 of 122 orders and returning buyers 16 of 17. Most unpaid buyers reached the payment screen and tapped nothing. So the pay step is built for a first-time buyer who doesn't know us yet:
  - The bank tap creates the order. An order that was submitted but never got a payment choice can't exist.
  - Bank apps come first, ranked by what opens in the current browser. Inside Facebook that means Khan, TDB and Xac first, with wallets that never hand off from Facebook further down. Khan opens fine from Facebook on current iPhones. No "open in Safari" button.
  - Save QR and transfer go below the bank apps. The transfer description is the payment number, copied with one tap.
  - The pay screen says who we are: the shop phone to call, when delivery comes, how many orders we've delivered, and what happens after paying. Nothing beyond what's true today.
  - `/pay/<n>` is server-rendered, so the amount and the options show before JS.
- Redesign the sidebar and every other cursed bit, not just checkout.
- SEO pages that drive sales, not pages for the sake of pages.
- Photos look better than they do now: resized properly, high quality, `fetchpriority` on the main image, explicit sizes.
- Recommended products are good and always work. Right now they're basic and broken half the time.
- The numbers I hold it to: Lighthouse mobile 95 or better on home, category and product. From PostHog web vitals at p75: LCP under 2.0 s, INP under 150 ms, CLS under 0.05. At most 45 KB of gzipped JS on listing and product pages and 60 KB on checkout, enforced by size-limit. Fonts under 50 KB. Proxy loss under 2%.

### Data

- PostHog gets used way more. All product and sales analytics live there.
- PostHog runs through a proxy on our own domain so adblockers don't eat events.
- Money events fire from the server. The PostHog person id is our customer id, never a phone hash, because an 8-digit phone hash reverses in seconds.
- Revenue comes from the Postgres ledger synced into PostHog's warehouse. Events carry the funnel and attribution.
- When I ask an agent about sales, it answers from PostHog. Agents shouldn't grind raw SQL to tell me what sold last week.

### How agents work here

Agent experience is the point of the whole rebuild. Every choice gets judged by whether the next agent ships faster and breaks less.

- Machine-checkable rules over docs. One check command. Short AGENTS.md.
- Use a library before custom code. No backward compatibility. Delete code.
- Gut, don't port. Old code tells you what a feature does, and its bugs are listed in `audit.md`. New code never copies it, except amerik-vitamin's Effect code, which this plan names. Delete anything no deployed Worker uses as soon as you find it (G0). Each live old app goes in the PR that replaces it in prod, and until then it keeps working, because customers order through it every day.
- No unit tests. The test is e2e against the PR's deployed preview.
- A Bash hook blocks the commands agents keep getting wrong.
- No erxes-specific rules. Only generic lessons carry over.
- Work runs as T3 delegates, each in its own worktree under `~/dev/scratchpad/vit-store`. Never in `~/dev/vit-store`, the main checkout.
- Never point local runs at production mutations. Never write to the prod database without my OK.
- Upstream bugs are mine to report. When Solid 2, frames, the router, the vite plugin, Effect, UI SDK, Alchemy, Drizzle or Pi breaks or acts strange, stop and tell me. Bring a minimal repro in `~/dev/scratchpad/vit-store/upstream/<package>-<short-name>/`, the exact versions, what you expected and what happened, and the source line you think is wrong. Search the upstream issues first and link any match. A workaround in our code is fine to keep moving, but it carries a comment linking the upstream issue, and it gets deleted when the fix ships. I file the issues and PRs myself. Agents don't open them.
